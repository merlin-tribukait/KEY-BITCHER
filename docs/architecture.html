Architecture

💬

Error message #42: "Your .env has opinions. Your .env is wrong."

This page explains why the tool is shaped the way it is, not just what it
does.

The problem it solves

A working AI setup needs several independent pieces of state:

  • provider API keys (many providers, many backups per provider),
  • a shared canonical copy so multiple machines/people agree on the key set,
  • the Wave terminal's cloud secret store,
  • your local .env,
  • knowledge about whether each key is still valid.

The naive approach — paste keys around — fails silently: keys expire, get
typo'd, or one machine gets updated and the next doesn't. key-bitcher
makes the bucket the single source of truth and turns every other store
into a derived, verifiable copy.

Core ideas

1. Bucket is the source of truth

.env, the Wave store, and every machine are all projections of the bucket
object. You never edit secrets at the edge — you upload, then
sync-secrets everywhere. Versioning on the bucket means a bad upload is a
recovery step, not a disaster.

2. Failover via key alternates

Providers ship multiple keys (OPENAI_API_KEY, OPENAI_API_KEY_2, ...).
benchmark tries every key per provider, promotes the first working one,
and leaves the rest as hot spares. This is why expired keys degrade
gracefully instead of breaking the whole flow.

3. Validation at the boundary

import-md is the dangerous moment — a human pasting keys. The parser
enforces ## Section structure, supports NAME: value and NAME=value
forms, and detects duplicates. validate --source s3|env re-checks the
bucket and .env for the same class of mistakes. Garbage is rejected before
it is uploaded, not after.

4. Stateless commands, auditable actions

Every subcommand does exactly one thing, so it composes in scripts, CI, and
IDE tasks. A command that "might also do something else" is harder to reason
about and easier to misfire. --dry-run / --print-exports modes exist so
you can preview before mutating.

5. Safety rails

  • The append-only log is size-rotated (bounded disk use).
  • key-bitcher-notifications.md and .env are gitignored.
  • CI runs a gitleaks scan on every push (see Security).
  • The S3 client uses rustls-ring (no OpenSSL dependency, fewer supply-chain
    attack surfaces).

Module map

Module Responsibility
src/main.rs CLI parsing (clap), command dispatch, auto flow
src/config.rs key-bitcher.toml, LoggingConfig, section overrides
src/secrets.rs the secrets.json model, serialization, key logic
src/workingmd.rs the working.md parser
src/s3.rs S3/B2 client (rustls), upload/download, versioning check
src/benchmark.rs provider health checks + key promotion
src/rust_setup.rs machine bootstrap (toolchain, integrations)
src/logging.rs rotating file logger

Why Rust

  • Single static binary, no runtime, trivial to distribute in release.yml.
  • rustls lets us talk to S3 without OpenSSL; fewer CVEs than a shared C
    stack.
  • Strong typing on the config/secrets models catches misconfiguration at
    compile time rather than at 3 a.m. during a rotation.
