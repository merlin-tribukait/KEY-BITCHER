Command reference

💬

Error message #42: "Your .env has opinions. Your .env is wrong."

Every command, its flags, and when to reach for it.

Global flags

key-bitcher [OPTIONS] [COMMAND]
Flag Default Description
--config <PATH> ./key-bitcher.toml Path to the config file
--auto-sync off Enables the automatic flow for sync commands
--debug, -d off Verbose logging to stderr
--log-file <PATH> key-bitcher.log Append-only log; rotated at [logging] max_size_bytes

No command — the auto flow

Running key-bitcher with no command executes the full pipeline:

  1. sync-secrets — pull canonical keys from S3 into .env
  2. wave-import — push them into the Wave secret store
  3. benchmark — verify each provider still accepts the keys

Why: the daily refresh you will run most often is "make everything match
and tell me what's broken", which is exactly this sequence.

sync-secrets

Fetch secrets from the S3 bucket and write them to .env.

key-bitcher sync-secrets [--dry-run] [--print-exports]
Flag Description
--dry-run Show what would be written without touching .env
--print-exports Print shell export KEY=value lines instead of writing .env

Why: .env is what your local tools (terminals, IDEs, AI agents) read.
This is the primary way a fresh machine gets its keys.

benchmark

Ping each configured model and report per-key/per-provider status.

key-bitcher benchmark

Models come from [benchmark] models in key-bitcher.toml. Providers
detected as expired (HTTP 401) are reported so you can rotate them.

Why: keys expire without warning. A 30-second health check turns "my agent
randomly stopped working" into "OpenRouter is expired, rotate it".

wave-import

Import .env keys into the Wave secret store.

key-bitcher wave-import

Requires the Wave terminal's wsh CLI (resolved from PATH or
[wave] wsh_path). Only keys that map to a known Wave provider preset are
imported.

Why: Wave agents run in a cloud sandbox that cannot read your local .env.
They read secrets from the Wave store, so importing keeps cloud sessions
configured without copying keys by hand.

import-md

Parse a working.md handout into structured secrets and upload them to the
bucket. The keys are parsed and uploaded in memory — nothing is written to
disk, so no intermediate secrets.json is left behind.

key-bitcher import-md --file PATH

The parser understands ## Section headings (and ### subsections),
NAME: value and NAME=value lines, and fenced code blocks. Section names
map to env-var names through the built-in table, overridable via
[sections] in the config.

Why: teams frequently receive keys as a chat dump. import-md turns an
unstructured paste into a versioned, uploaded, auditable key set — and it
catches copy/paste mistakes (duplicate keys, mismatched values) before they
reach the bucket.

list

List the secret names in the bucket.

key-bitcher list

Prints only names and value lengths — never values.

Why: a safe way to see what the canonical store contains (for example in
logs or on a shared screen) without exposing the keys themselves.

secure

Restrict file permissions on .env / secrets.json to the current user.

key-bitcher secure [--paths PATH ...]

Defaults to .env and secrets.json. On Windows this drops inherited ACLs
and grants read access to the current user only.

Why: on shared machines, other local users should not be able to read
your key files. This command makes the OS-level hardening a one-liner
instead of a manual icacls ritual.

upload

Upload a secrets JSON file to the bucket.

key-bitcher upload --file PATH

Why: publishing a new canonical key set (after rotation) so every machine
can sync-secrets it.

validate

Dry-run checks that .env or the bucket is consistent.

key-bitcher validate --source env|s3

Checks format, duplicates, and structural expectations without writing or
uploading anything.

Why: a cheap pre-flight for CI or before a demo; catches a half-written
.env or a malformed bucket object.

wave-test

Self-test the Wave secret-store integration.

key-bitcher wave-test

Why: isolates Wave connectivity problems so you don't confuse them with
bucket or .env problems.

s3-versioning

Verify the bucket has versioning enabled (recovery safety net).

key-bitcher s3-versioning

Why: versioning means an accidental overwrite of the canonical key set is
recoverable. This command confirms the safety net exists.

s3-test

Connectivity test against the bucket (credentials + reachability).

key-bitcher s3-test

Why: the first thing to run when sync-secrets fails — separates "bad
AWS keys" from "wrong bucket/region".

create-bucket

Create the bucket if it does not exist, with versioning enabled.

key-bitcher create-bucket

Why: first-time setup on a new account, so the rest of the tool has a
place to write.

rust-setup

One-shot environment bootstrap.

key-bitcher rust-setup

Installs/checks the Rust toolchain, cargo tools, and the shell integrations
(env-loader.ps1, install-path.ps1).

Why: a fresh machine should be usable in one command instead of a wiki
page of manual steps.
