Build & test

.\build.ps1 -Profile release -Clippy -Test -Fmt

This runs, in order:

  1. cargo fmt --check
  2. cargo clippy --release -- -D warnings
  3. cargo test --release
  4. cargo build --release

Or run the pieces individually:

cargo build --release
cargo test
cargo clippy --release -- -D warnings
cargo fmt

Code layout

See Architecture for the module map. The important entry
points:

  • src/main.rs — clap definitions (global flags + Commands enum) and
    dispatch. Add a subcommand by extending the enum and matching it here.
  • src/config.rs — config structs that deserialize key-bitcher.toml;
    additive optional fields keep old configs working.
  • src/secrets.rs — the secrets.json model. This is the canonical key set.
  • src/workingmd.rs — the working.md parser. New section-name mappings go
    in its built-in table (or via [sections]).

Testing strategy

Unit tests live next to the code they cover (config, secrets,
workingmd). CI runs them on Ubuntu and Windows. A new parser feature or key
transformation must ship with tests — this is a secrets tool, and a
silent copy/paste bug is the class of bug it exists to prevent.

CI

.github/workflows/ci.yml:

  • gitleaks job — scans the push for secrets, fails on findings.
  • build job — matrix over ubuntu-latest and windows-latest, runs
    fmt --check, clippy -D warnings, test, build.

.github/workflows/release.yml — builds release binaries for Ubuntu and
Windows and publishes a GitHub release on tags.

.github/workflows/pages.yml — builds the Jekyll site in docs/ and deploys
it to GitHub Pages (source must be set to GitHub Actions in repo
settings).

.github/dependabot.yml — weekly updates for Cargo and GitHub Actions.

Contributing

  1. Open an issue first for anything non-trivial (the issue list doubles as
    the roadmap — see the README and the
    issues page).
  2. Keep commands single-purpose; add --dry-run modes, not side effects.
  3. Never print or log key values — the logging layer must stay
    value-free.
  4. Follow the format/clippy gates; they are enforced in CI.

Release process

  1. Update Cargo.toml version and add a CHANGELOG.md entry.
  2. Tag: git tag v0.x.x && git push --tags.
  3. release.yml builds and attaches the binaries to a GitHub release.
